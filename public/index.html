    The data: All of Us and the OMOP tables

    You will learn

    • how concept IDs connect records to codes and names;
    • the difference between source and standard concepts, and why your guides use source concepts for diagnoses.

    One table per kind of record

    The All of Us EHR data uses the OMOP Common Data Model. Instead of one big table per person, there is one table per kind of event, and every row is one record: a diagnosis entered at a visit, a prescription, a lab result. Each row carries a person_id, a date and a concept ID that says what the record is.

    Concept IDs: records store numbers, the concept table explains them

    A diagnosis record doesn’t say “E11.9”. It stores a number such as 1001, and the concept table says that 1001 is vocabulary ICD10CM, code E11.9, “Type 2 diabetes mellitus without complications”. To find records by code, you join the records to concept (Module 3).

    Source or standard concept?

    Every diagnosis has two IDs. condition_source_concept_id is the code the clinic entered (ICD-9 or ICD-10). condition_concept_id is that code mapped to a SNOMED “standard” concept. Your code lists are written as ICD patterns (E11, F32, G30), so your guides join on the source concept. Drugs are the other way round: drug_concept_id is a standard RxNorm concept whose name contains the ingredient, so your guides match drug names with regular expressions.

    SQL 1: asking a table questions

    You will learn

    • SELECT, FROM, WHERE, ORDER BY and LIMIT;
    • conditions with AND, OR, IN, BETWEEN and IS NULL;
    • matching codes with patterns (regular expressions);
    • counting rows and people.

    The shape of every query

    SELECT person_id, year_of_birth      -- which columns
FROM person                          -- which table
WHERE year_of_birth < 1955           -- which rows
ORDER BY year_of_birth               -- in what order
LIMIT 10;                            -- at most how many

    SQL describes the result you want, and the database works out how to get it. The clauses are written in the order above, but they are applied in this order: FROM (pick the table) → WHERE (keep rows) → SELECT (compute columns) → ORDER BY (sort) → LIMIT. That’s why you can’t use a column alias from SELECT inside WHERE.

    Conditions

    You writeMeaning
    gender_concept_id = 8532equal (8532 = FEMALE)
    year_of_birth <> 1950not equal
    a AND b, a OR b, NOT acombine conditions; use brackets when mixing AND and OR
    person_id IN (1, 4, 12)one of a list; the list can be a whole query
    condition_start_date BETWEEN '2018-01-01' AND '2018-12-31'a range, both ends included
    visit_occurrence_id IS NULLmissing. = NULL never works.

    Dates are stored as text in the form 'YYYY-MM-DD', so comparing them as text gives the right order: '2017-06-01' < '2018-01-15'.

    Counting

    SELECT COUNT(*) AS records,                      -- rows
       COUNT(DISTINCT person_id) AS people          -- different people
FROM condition_occurrence;

    Matching codes with patterns

    Your code lists are regular expressions: short patterns that describe many codes at once. BigQuery tests them with REGEXP_CONTAINS(text, r'pattern'); the r means a “raw” string, so backslashes are passed through unchanged.

    Pattern pieceMeansExample from your guides
    ^starts with^N18: CKD codes N18.x
    |or^(F32|F33): depression
    \.a literal dot (a bare . means “any character”)^G31\.84: MCI
    [123]one of these characters^F0[123]: F01, F02, F03 (dementia)
    ( )groups alternatives^(296\.[23]|300\.4|311): ICD-9 depression

    For drug names, the guides lower-case the name first: REGEXP_CONTAINS(LOWER(concept_name), r'sertraline|fluoxetine|…'). A pattern without ^ matches anywhere in the text, which is what you want for an ingredient inside a long product name.

    Predict, then reveal: why does LIKE fail here?
    SELECT concept_code FROM concept WHERE concept_code LIKE 'F3%';

    LIKE uses % as “anything”. In All of Us, 'F3%' would match F32 and F33, but also F31 (bipolar disorder) and F34.0 (cyclothymia), which are not in your depression definition. A regular expression lets you say exactly ^(F32|F33|F34\.1).

    SQL Module 3

    SQL 2: joining and summarising

    You will learn

    • how joins combine tables, and why they can repeat rows;
    • INNER vs LEFT joins, and their R twins;
    • GROUP BY with MIN, MAX and COUNT, and HAVING.

    See a join happen

    A join matches rows of two tables on a key, here person_id. Try each type and watch which rows survive.

    Why joins matter so much

    Almost every bug in a cohort build is a join that dropped people (INNER where LEFT was needed) or multiplied rows (a key that isn’t unique). Before any join, ask: how many rows per key does each table have?

    Joining records to their codes

    SELECT co.person_id, co.condition_start_date, c.concept_code, c.concept_name
FROM condition_occurrence AS co                      -- "co" is a short alias
JOIN concept AS c ON c.concept_id = co.condition_source_concept_id
WHERE c.vocabulary_id = 'ICD10CM';

    Aliases (co, c) keep queries short and say which table each column comes from. You need them whenever two tables share a column name.

    One row per person: GROUP BY

    GROUP BY person_id collects each person’s rows into a group; aggregate functions then summarise each group: COUNT(*), MIN(date) (first date), MAX(date) (last date), COUNT(DISTINCT date) (number of days). Every column in SELECT must be either in GROUP BY or inside an aggregate.

    Predict, then reveal: a list of people inside another query
    SELECT person_id, drug_exposure_start_date
FROM drug_exposure
WHERE person_id IN (SELECT DISTINCT co.person_id
                    FROM condition_occurrence AS co
                    JOIN concept AS c ON c.concept_id = co.condition_source_concept_id
                    WHERE REGEXP_CONTAINS(c.concept_code, r'^(E11|250)'));

    Drug records only for people who have a diabetes code. The inner query returns a list of person_ids; IN keeps rows whose person is in that list. This is exactly your guides’ DM_PEOPLE, used to keep every query restricted to people with diabetes.

    SQL Module 4

    SQL 3: time windows and latest values

    You will learn

    • CTEs (WITH): building a query in named steps;
    • windows of time around each person’s own time zero;
    • the latest value before time zero (window functions);
    • CASE WHEN and UNION ALL, the two tricks behind the baseline query.

    Named steps with WITH

    WITH dep AS (                          -- step 1: each person's time zero
  SELECT person_id, MIN(condition_start_date) AS t0 FROM ... GROUP BY person_id),
labs AS (                              -- step 2: labs near each time zero
  SELECT ... FROM dep JOIN measurement ...)
SELECT * FROM labs;                    -- final step

    A CTE is like an R object made on one line and used on the next, except it only lives inside this one query. Your baseline query has five: pop, lc, labs, lab_last, meds, visits.

    Windows of time around time zero

    Each person has their own time zero, so windows are written relative to it: join the people-with-t0 table to the records, then filter dates against t0. In BigQuery, DATE_SUB(t0, INTERVAL 365 DAY) is the date one year earlier and DATE_ADD(t0, INTERVAL 90 DAY) is 90 days later.

    Window in your guidesConditionWhy the boundary is where it is
    Medicines, visits: year beforedate < t0 AND date >= DATE_SUB(t0, INTERVAL 365 DAY)strictly before t0: a prescription on day 0 may be the treatment decision
    Labs: last value in 2 yearsdate <= t0 AND date > DATE_SUB(t0, INTERVAL 730 DAY)a lab on the day of time zero describes the person at the decision
    New user: no antidepressant in the year beforeno record with date < t0 AND date >= t0 − 365everyone starts at the same decision point
    Grace period (3a)date >= t0 AND date <= DATE_ADD(t0, INTERVAL 90 DAY)prescribed at the diagnosis visit counts
    Outcomesdate > t0after time zero only; earlier events are history (covariates)

    The latest value before time zero

    A window function numbers rows within each person without collapsing them: ROW_NUMBER() OVER (PARTITION BY person_id ORDER BY measurement_date DESC) gives 1 to each person’s newest row, 2 to the next, and so on. Keep rn = 1.

    CASE WHEN: if–then inside SQL

    CASE WHEN lc.lab = 'hba1c' AND LOWER(u.concept_name) LIKE '%per mole%'
       THEN m.value_as_number / 10.929 + 2.15        -- mmol/mol to %
     WHEN lc.lab = 'creatinine' AND LOWER(u.concept_name) LIKE '%micromole%'
       THEN m.value_as_number / 88.42                -- µmol/L to mg/dL
     ELSE m.value_as_number END AS value

    The first true WHEN wins; ELSE covers everything else. R’s case_when() works the same way (Module 6).

    UNION ALL: stacking results

    UNION ALL puts the rows of one query under the rows of another. Both must have the same columns in the same order. The baseline query stacks labs, medicines and visits into one long table of row_id, item, value, so all three come back in a single download.

    R writes the SQL

    Your guides never type a full query by hand. R builds the text with glue(): anything inside { } is replaced by the value of an R expression before the text is sent to BigQuery.

      WHERE vocabulary_id = 'ICD10CM' AND REGEXP_CONTAINS(concept_code, r'{x$icd10}')")

      WHERE vocabulary_id = 'ICD10CM' AND REGEXP_CONTAINS(concept_code, r'^(F32|F33|F34\.1)')
    Why build SQL in R?

    One code list drives every query, the CDR version is set once in Part 0, and a function like first_dates_sql(sets, people_sql) can be reused across all three aims. To see the SQL any function makes, print it: cat(first_dates_sql("depression", DM_PEOPLE)).

    The drug-days query

    dc_sql <- paste(sprintf("SELECT concept_id, '%s' AS cls FROM `%s`.concept
                         WHERE domain_id = 'Drug' AND REGEXP_CONTAINS(LOWER(concept_name), r'%s')
                           AND NOT REGEXP_CONTAINS(LOWER(concept_name), r'%s')",

    sprintf() fills each %s in turn, once per drug class (it is vectorised over names(DRUG_REGEX)), and paste(…, collapse = "UNION ALL") glues the class queries into one. For classes without an exclusion, excl_of() returns ^$, a pattern that only matches an empty name, so nothing is excluded.

    Why row_id and not person_id?

    One person can be in both trials with different time zeros: their depression date in 3a, their first antidepressant in 3b. Covariates differ between those two time zeros, so the guides give each person × question its own row_id and join covariates by row_id. Joining by person_id would mix them up.

    Building the analysis dataset: follow-up, censoring, intervals

    You will learn

    • how follow-up time and status are computed, and what censoring and competing events mean;

    Time-to-event data

    “What % had hypoglycemia?” is the wrong question when people are followed for different lengths of time. Instead, each person contributes time at risk from time zero until the first of: the event, death, the end of their records, or the 5-year cap.

    statusMeaningExample
    1the event happenedfirst hypoglycemia episode on day 280
    2competing event: died firstdeath on day 200, no hypoglycemia before
    0censored: we stopped watchingrecords end on day 400, or the 5-year cap

    R fu() as a calculator

    Risks with a competing event

    Kaplan–Meier treats death like censoring, as if the dead might still have hypoglycemia later. So 1 − KM overstates the risk. The Aalen–Johansen estimator splits people into “had the event”, “died first” and “still at risk”, and gives the cumulative incidence: the proportion with the event by each time. In R, survfit(Surv(time, factor(status, 0:2, c("censor", "event", "death"))) ~ arm, weights = w) does this when the status is a factor with a censoring level first.

    Start–stop (counting-process) data

    When something changes during follow-up (a weight, a period, an exposure), a person’s time is split into intervals, one row each: tstart, tstop, event. The event is only marked on the interval in which it happens. Models then use Surv(tstart, tstop, event).

    R survSplit at 6 months (Part 8, H3c)

    In your thesis
    • Aim 2: follow-up is split where hypoglycemia exposure switches on (1 year after the first episode), so exposure is time-varying.
    • Aim 3a: clone data are split into 15-day intervals during the grace period, because each interval gets its own censoring weight.
    • Aim 3c: follow-up is split at 6 months to estimate early and later effects.

    Multiple imputation

    mice() fills each missing value with a plausible draw, predicted from everything else, including treatment and outcome. It does this m times (5 for drafts, 20 for the final run). Each completed dataset is analysed separately and the results are combined with Rubin’s rules (Module 10).

    meth <- make.method(df);  meth[!names(meth) %in% IMPUTE] <- ""   # impute only these columns
pred <- make.predictorMatrix(df); pred[, "row_id"] <- 0            # row_id predicts nothing
imp  <- mice(df, m = M_IMP, method = meth, predictorMatrix = pred, maxit = 10, seed = 2026)
complete(imp, 1)                                                   # the first filled-in dataset
    Why the outcome is in the imputation model

    If HbA1c is imputed without knowing who had hypoglycemia, the imputed values carry no link to the outcome, and the estimated effect of HbA1c (and anything correlated with it) is pulled toward zero. Using the event indicator and the Nelson–Aalen cumulative hazard as predictors keeps that link.

    The one rule that prevents most biases

    At time zero, three things must happen together: the person meets eligibility, is assigned a strategy, and starts follow-up. If follow-up starts before treatment is known, or eligibility uses information from after time zero, bias creeps in. The best-known form is immortal time.

    Confounding and the propensity score (3b)

    Doctors don’t choose SSRIs at random: age, calendar year, insomnia and kidney function all play a part, and several of those also affect hypoglycemia. The propensity score is each person’s probability of getting an SSRI given their covariates, estimated with logistic regression (glm(treat ~ ns(age, 3) + ns(cal_year, 3) + …, family = binomial())). Weighting people by their propensity score makes the two arms look alike on every covariate in the model.

    Stats Weights from one propensity score

ess   <- function(w) sum(w)^2 / sum(w^2)          # effective sample size

    Effective sample size (ESS): weighting makes some people count more than others, so a weighted sample carries less information than the same number of equal people. ESS gives the equivalent number: for example, 1,000 weighted people might carry the information of about 850.

    Checking balance: the standardized mean difference

    For each covariate: the difference in means between arms, divided by the pooled SD. Unlike a p-value it doesn’t depend on sample size. After weighting, every |SMD| should be below about 0.1.

    Stats SMD calculator

    Reading a balance table

    A typical pattern: before weighting, people who start treatment differ from those who don’t, say an SMD of −0.20 for insulin use. After weighting, the largest |SMD| drops to about 0.04: balanced on everything measured. Overlap weights balance every covariate in the propensity model exactly, so after them all SMDs are essentially 0.

    Immortal time, and why 3a needs clones

    3a compares “start within 90 days” with “don’t”. Suppose you simply compared people who did start with people who didn’t, from the depression date. Someone who started on day 60 had to stay event-free and alive for 60 days in order to become a starter. Those 60 “immortal” days make starting look protective even when it does nothing.

    Clone–censor–weight fixes this:

    1. Clone: at time zero, copy every person into both strategies. The arms are identical at baseline.
    2. Censor: stop following a clone on the day the person’s actions break its strategy. The “don’t start” clone is censored the day they start (if within 90 days); the “start” clone is censored at day 90 if they haven’t started.
    3. Weight: censoring isn’t random, because people who start differ from those who don’t. Each remaining clone is weighted by 1 / P(still following the strategy), from a model of who starts treatment, fitted in 15-day steps (ccw_S()). These are inverse probability of censoring weights (IPCW).

    Stats Follow one person’s two clones

    Try these
    • Start day 45, event day 30: the event happens before any deviation, so it counts in both clones.
    • Start day 120: “start within 90 days” is broken at day 90, while “don’t start” is followed even though they start later.
    • Never starts, event day 200: only the “don’t start” clone sees the event.

    Per-protocol vs intention to treat

    Intention to treat (3b) follows everyone in the arm they started, whatever they do later: it estimates the effect of starting an SSRI vs bupropion/mirtazapine. Per-protocol (3a) estimates the effect of following a strategy, which needs censoring and weights for people who deviate.

    “Was this episode caused by insulin or by the antidepressant?”

    The design never asks that about a single episode. Nearly every episode happens on a diabetes drug, in both arms. Because the arms are balanced on every diabetes drug class, a recently started drug (new_gld), HbA1c, kidney function and earlier hypoglycemia, the difference in risk between arms is the effect of the antidepressant strategy, including interactions such as an SSRI raising sulfonylurea levels.

    Risks and differences: read them off the curves

    • Risk at 2 years: the height of a curve at 2 years. A made-up example: 4.0% if everyone started vs 3.0% if nobody did.
    • Risk difference: 4.0 − 3.0 = +1.0 percentage point, 1 extra person per 100 over 2 years. This is the number that matters to patients.
    • Risk ratio: 4.0 / 3.0 = 1.33.
    • Hazard ratio: the ratio of instantaneous event rates, averaged over all follow-up, say 1.40 (1.02–1.92). It uses all follow-up (up to 5 years), so it has more events and a narrower interval than the 2-year risks.

    The weighted Cox model

    coxph(Surv(time, status == 1) ~ treat, data = d, weights = w, cluster = id)
    • Surv(time, status == 1): the event is status 1. Death (2) and censoring (0) both end follow-up here; the Cox model estimates the cause-specific hazard.
    • weights = w: overlap weights (3b) or censoring weights (3a).
    • cluster = id: robust standard errors. With weights, and with each 3a person appearing as two clones, ordinary SEs are too small; clustering by person fixes that.
    • The coefficient is a log hazard ratio: exp(coef) is the HR.

    Uncertainty: bootstrap and Rubin’s rules

    The bootstrap redraws people with replacement (di[sample(nrow(di), replace = TRUE), ]), reruns the whole analysis, weights included, and repeats B times. The spread of the B estimates is the standard error. It is used for the risks, which have no simple formula once weights are involved.

    How sure can we be? E-values and negative controls

    Weights only balance what was measured. Depression severity isn’t in the EHR. The E-value asks how strong an unmeasured confounder would need to be to explain the result away.

    Stats E-value calculator

    A negative control outcome is something treatment can’t plausibly cause. A cataract HR near 1, say 0.97 (0.80–1.18), shows no sign that starters simply had more diagnoses recorded (detection bias). Note what it can’t rule out: confounding specific to hypoglycemia, such as frailty.

    The measures in Aims 1 and 2

    • Aim 1, rate ratio (Poisson regression): hypoglycemia episodes per person-year in each year before the index date, cases vs controls. The model has the form glm(n_hypo ~ case * ns(year, …) + matching factors + offset(log(py)), family = poisson); the offset turns counts into rates, and the case × year term lets the rate ratio change across the 10 years.
    • Aim 2, RERI (additive interaction): with HR₁₁ for both hypoglycemia and depression, HR₁₀ and HR₀₁ for each alone, RERI = HR₁₁ − HR₁₀ − HR₀₁ + 1. A RERI of 0.5, for example, means people with both had 0.5 “extra” relative risk beyond the sum of the two separate effects: public-health synergy, even without multiplicative interaction.

    Every saved results file (aim3_*.csv, the forest plot) holds model estimates or masked counts. Before exporting anything else, check for counts of 1–20, and for rates or percentages computed from such counts, which can reveal them.
